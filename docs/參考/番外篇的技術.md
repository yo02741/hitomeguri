# 番外篇的技術（像素散步與像素遊戲）

整理日期：2026-10-17（番外篇 P4 收尾時）。給之後要改 `/about` 的像素散步或 `/play` 的像素遊戲的人：用了什麼技術、怎麼做的、量到的數字、還有哪些限制。

規格（畫面上長什麼樣子、使用者的決定）以 [DESIGN.md](../../DESIGN.md) §14a（像素散步）、§14b（番外篇）為準；這份只講做法。驗收怎麼看在 [docs/驗收.md](../驗收.md)「形象網站：像素散步」「番外篇：像素遊戲」。開發時用到的 skill 與多 agent 流程在 [skill-回顧.md](skill-回顧.md)。

## 1. 點陣畫布

`Gfx` 是一塊 `Uint32Array`，一格一個顏色，0 是透明。所有圖形畫在整數座標上，不反鋸齒、不用 canvas 的透明度。像素的格式是 little-endian 的 `0xAABBGGRR`，剛好就是 `ImageData` 的位元組順序，所以同一塊記憶體不用複製就能交給 canvas：

```ts
// views/PlayView.vue 的 paint()：遊戲畫好一格，整張貼上去
image = new ImageData(new Uint8ClampedArray(f.buf.buffer, f.buf.byteOffset, f.buf.byteLength), f.w, f.h)
ctx.putImageData(image, 0, 0)
```

- **抖色**：漸層（天空、夕陽）、半透明（影子、暫停的遮罩、取景框外變暗）、淡出淡入都用 Bayer 4×4：

  ```ts
  const BAYER = [0, 8, 2, 10, 12, 4, 14, 6, 3, 11, 1, 9, 15, 7, 13, 5]
  export const dotOn = (x: number, y: number, level: number) => BAYER[((y & 3) << 2) | (x & 3)]! < level
  ```

  `level` 0–16，越大越滿。淡出淡入是 16 級的墨色抖色；換時段時用抖色在 1.2 秒內從舊時段的畫面淡到新時段（下一個時段的 tile 先放進快取）。
- **放大**：邏輯高 160（GBA 是 240×160），寬照容器算。canvas 的實際大小就是邏輯大小，CSS 放大整數倍並加 `image-rendering: pixelated`。
  - 像素散步：`floor(寬 / 180)` 與 `floor(min(視窗高 × 0.55, 480) / 160)` 取小的，最少 2（1280 寬 3 倍、390 寬 2 倍）。
  - 遊戲（`game/ui/layout.ts`）：桌機 1280×800 是 4 倍；手機直拿照寬算倍數（390 寬 2 倍），邏輯高在 160–256 之間變高，控制區貼在下面；打橫放不下 2 倍時用四分之一一級的倍數（740×300 是 1.75 倍），不掉到 1 倍。
- **sprite**：用字元畫，一個字元對一個 px token，存成索引（`Uint8Array`）＋用到的 token 名單，畫的時候才查目前的調色盤，所以同一張 sprite 白天、黃昏、夜晚自動換色。圓的、會動的東西（頭、車、動物）用 `drawSprite` 拿 `Gfx` 指令畫，畫完自動描一圈 `px-ink` 的外框。

  ```ts
  sprite(`
    ..kk..
    .kwwk.
  `, { k: 'ink', w: 'white' })
  ```
- **字**：像素散步畫在 canvas 上的是 3×5 點陣字；遊戲的介面（對話框、手帳、面板）是 DOM，字型是 Google Fonts 的 DotGothic16（只在 `/play` 載入），尺寸用 `--u`（一個邏輯像素是幾個 CSS px）乘上去，跟著畫面一起放大。

## 2. 顏色：token 與時段

- 程式裡不寫色碼。顏色名單是 `PX`（83 個：墨、紙、石、木、屋瓦、朱、金、葉、海、櫻、楓、雪、三個時段的天空、燈、霓虹…，番外篇加了赤瓦、珊瑚、礁湖、疊、寒緋櫻、柏油、雪的陰影等 20 個），值在 `theme.css` 的 `--color-px-*`。執行時 `readTokens()` 用 `getComputedStyle` 讀出來；正式站的 CSS 會被壓縮（`#fff`、`red`），所以 `parseColor` 讀得懂三碼、六碼、`rgb()`，顏色名字交給一個 canvas 換成六碼。
- `game/rules.test.ts`、`pixelwalk.test.ts` 掃 `web/src/game`、`components/game`、`PlayView` 的 .ts／.vue／.css，抓三碼、六碼與顏色名。例外只有旅人 sprite：它的 RGB 是從旅人自己的 SVG token 解析出來的，是資料不是寫死的色碼。
- **時段換色**是 GBA 的做法：換整組調色盤，不是在畫面上疊一層半透明。

  ```ts
  /** 時段的換色：往色調混多少、整體亮度 */
  const TIME = { day: [0, 1], dusk: [0.2, 0.9], night: [0.5, 0.62] } as const
  // 天空、燈、霓虹、星、月不混色（UNTINTED），所以夜裡的燈是亮的
  ```

  黃昏把每個顏色往 `--color-px-tint-dusk` 混 20% 再乘 0.9，夜晚往 `tint-night` 混 50% 再乘 0.62。旅人 sprite 的 RGB 用同一個公式（`tintRgb`）。室內一律用白天的顏色。

## 3. 像素散步（`/about`）怎麼動

像素散步跟遊戲共用畫布、調色盤、sprite、亂數（打包成 4 KB 的 `pxcore`），但它不是 tile 地圖，是一條往右捲的長條：

- **一區一條長條**：10 區（北海道、白川鄉、東京、鎌倉、富士山、京都、奈良、大阪、宮島、沖繩），每區地面長 1,400–1,500 格。進到一區時用新的種子把整條畫好（約 10 ms），之後每一格只是照捲動位置貼上（寬 480 約 0.7 ms）。同一區每次去，房子、樹、地標的排法都不一樣。
- **景深**：天空不動，2–4 層背景的捲動速度 0.06–0.55，地面 1，前景 1.3（畫在旅人前面，旅人停下來時被樹幹、電線桿擋住的部分用抖色透出來）。
- **季節、時段、天氣**：進一區時抽；腳本可以中途換（夕陽沉下去、驟雨、下雪），畫面用抖色淡過去 1.2 秒。重畫時佈景不能跑掉，所以畫長條時亂數不管時段、天氣都抽一樣多次（測試會檢查）。
- **腳本**：65 個 generator 腳本（各區 45 個、共用 20 個），同時最多一個「主要的」（旅人停下來互動）與一個「背景的」（天上、遠處）。挑之前可以先問 `ready`（前面有沒有鳥居、攤子、海），標籤對得上但不會有的地方用 `except` 排除（沖繩沒有狸貓）。
- **換區**：8 種轉場（淡出淡入、新幹線、渡輪、飛機、日本地圖、隧道、霧裡的大鳥居、翻頁），照兩區的地理挑；新幹線月台的站名用真的站。轉場卡住 25 秒直接換過去。
- **載入**：`PixelWalk.vue` 本身很小，引擎、各區、腳本捲到 600px 內才下載，先畫好第一格，進到畫面才開始走；捲出畫面、分頁在背景時停。減少動態的人一開始就是暫停的。
- **你的旅人**：登入、而且這台裝置有旅人快取（進過 `/play`）時，散步的人換成自己的旅人（16×24，朝右），夥伴跟在後面跳；只讀快取，不打 Firestore、不載 three.js。

## 4. tile 與 kit

- tile 16×16。每套 kit 用 `registerTileset` 註冊，id 全域唯一，一套一段 1024：

  | id | kit | 用在 |
  |---|---|---|
  | 1–1023 | 基本 | 草、路、石板、水、沙、台階、樹、柵欄、告示牌、拍攝點記號、門、室內的地板與櫃台 |
  | 1024–2047 | 近畿 | 京都、奈良、大阪、兵庫 |
  | 2048–3071 | 沖繩 | 沖繩 |
  | 3072–4095 | 室內 | 車站大廳、機場、店、授与所、旅館、你的房間 |
  | 4096–5119 | 關東 | 東京（延遲載入） |
  | 5120–6143 | 北海道 | 北海道（延遲載入；已經用到約 6116） |

- 多格的物件命名成 `<kit>/<名字>/<cx>,<cy>`，開花版叫 `<名字>@bloom`、格數一樣，花期一到整批換 tile（不另外畫花）。
- 地圖分四層：地面（不透明）、下層（牆、柵欄、建築下半）、角色（照腳底 y 排序）、上層（屋頂、樹冠、鳥居的橫木，畫在角色前面），最上面是天氣。另外一張 `Uint8` 的行為碼：`walk`、`block`、`water`、四個方向的 `ledge`、`door`、`counter`（隔著櫃台說話）、`sign`、`photo`、`grass`；查的順序是地圖的覆寫 > 上層 > 下層 > 地面。
- tile 的圖是程式畫的（`Gfx` 指令），第一次用到才畫進快取，key 是 id×季節×時段×動畫格×花樣×接邊；之後每格只 blit 看得到的範圍。快取超過兩萬格整個清掉重畫。
- 地標的樣子是 ASCII 藍圖（`gen/blueprints.ts`，一字一格、面向南），`gen/classify.ts` 先看資料的類型、類型不明確才看名字（「神社」「宮」「大社」、「寺」「院」、「城」…）。**資料沒寫的不畫**：城只畫石垣、城門、城跡的平房，不畫天守；名字有「塔」才畫塔；薰衣草田只畫在資料寫了花田、或在富良野・美瑛的鎮。
- 近畿、沖繩、室內在 `kits/core.ts`，一進 `/play` 就有；關東、北海道在 `kits/lazy.ts`，第一次去那一縣才 `import()`（另一個 chunk，gzip 約 18 KB）。

## 5. 地圖生成

### 選鎮（照真實資料）

一縣最多 9 鎮：起點的鎮 → 有名城蓋章地點的市区町村（最多 4 個，北海道 1 個）→ 沖繩一個離島 → 其餘照景點分數總和補滿；鐵路的縣要連得到起點，代表站跟已經選到的鎮一樣的不選；北海道用距離分散（鎮與鎮隔 30 km 以上、半徑 120 km 內最多 3 鎮）。同一個算法寫了兩份：前端 `world/towns.ts` 的 `TOWN_RULES` 與 pipeline `game_world.py` 的 `RULES`，pipeline 先選好寫進世界索引，前端的 vitest 拿 fixture 對過兩邊結果一樣。

### 一個鎮怎麼長出來（`world/gen/town.ts`）

1. **種子**：`seedOf(市区町村碼, GEN_VERSION)`（FNV-1a）餵給 mulberry32。整個生成只用這個亂數與座標的雜湊（`hash2`、`noise`），所以同一份資料每次都長得一樣。
2. **投影**：車站在中間、北朝上，景點離車站的距離用 log 壓縮，近的不擠在一起、遠的也放得進 44–64 × 34–48 格：

   ```ts
   const k = Math.log(1 + d / 0.6) / Math.log(1 + dmax / 0.6)   // d、dmax 是 km
   return { x: Math.round(cx + (o.x / d) * k * Rx), y: Math.round(cy + (o.y / d) * k * Ry) }
   ```
3. **地形**：只在資料能判斷時才畫。沖繩往海灘、岬、島、橋的方向是海；近畿只在資料有橋、或名字有「川」時畫河。
4. **擺東西**：車站（或巴士站、機場）、最多 12 個地標（大小看分數與文化指定）、店（旅館、食堂、老舖、茶屋）。每個地標前面一格是告示牌＋拍攝點。
5. **路**：車站、地標、店當節點，用曼哈頓距離做 Prim 的最小生成樹；再補最多 2 條環線——直線距離 4–26 格、但在樹上要繞 2.2 倍以上的兩點才連。每條邊用 A* 鋪：街上每格代價 3、走 2 格寬的直角街道；郊外代價 `2 + noise × 3`，路自然會彎。神社前拉直的參道。
6. **填空**：路邊成排的房子、田、樹林、灌木，用雜訊場決定哪裡放什麼；地圖邊一圈樹（沖繩靠海的一邊是深海）。
7. **人**：事實的人（祭典、老舖、名城的蓋章地點、平年的花期、到別鎮的距離）、路人、委託；祭典的月份多攤子、提燈、人。
8. **可達性**：從車站出口 flood fill，門、拍攝點、NPC、告示牌都要走得到；走不到就拆掉擋路的填空。vitest 把每一鎮都生成一次檢查。

### 鎖住已經上線的鎮

`GEN_VERSION` 從 P2 起一直是 2：存檔記著生成器版本，變了就要把玩家放回車站，所以上線的鎮不能變。`world/gen/snapshot.test.ts` 對京都、沖繩的 18 鎮算 FNV 雜湊（三層 tile 的名字、行為覆寫、實體、warp、室內、到站的地方、地標、開花、祭典的格子），再對近畿、沖繩、室內 kit 每個 tile 在四季 × 三時段畫出來的像素算雜湊。P3、P4 改到共用的生成器與畫法時，這個測試保證那 18 鎮一格都沒動；故意要改時才 `vitest -u`，並寫明理由。

## 6. 引擎

### 迴圈

```ts
// views/PlayView.vue：跟螢幕更新率無關，每秒固定 60 步；落後太多就丟掉（不會一口氣快轉）
const dt = Math.min(0.1, (now - (last || now)) / 1000)
acc += dt
let n = 0
while (acc >= 1 / 60 && n < 6) {
  game.update(1 / 60)
  acc -= 1 / 60
  n++
}
if (n === 6) acc = 0
```

分頁在背景、P 暫停時整個停；打開手帳、對話中世界停住，只在畫面有變化時重畫。固定步長讓 60 Hz、120 Hz 的螢幕手感一樣，也讓測試可以一步一步算。

### 走格子

- 時間用「更新次數」算：走一步 16 次（每次 1px）、跑 8 次、跳台階 32 次（兩格，最高 10px，地上有影子）。輕點方向只轉身，按住超過 6 次才走；走到一半輸入的方向、A、START、相機都先存著，到了那一格再處理，所以連續走不會頓。
- 移動中的角色同時佔著出發與目的地兩格，別人進不來；碰撞只算一格。撞牆是「咚」一聲原地踏一步。
- 夥伴走玩家剛離開的那一格；玩家回頭撞到就交換；被擋超過 1.5 秒直接放到下一格。

### A*（`engine/path.ts`）

點畫面上的格子時旅人自己走過去。目標可以是好幾格（走到 NPC 旁邊任何一格都算到），啟發函式是到最近目標的曼哈頓距離，open list 是二元堆積，最多展開 6,000 格。鄰居由呼叫的人給（一般一格、台階跳兩格、走不了回 null），所以碰撞規則只有一份。

### 腳本與事件

腳本是 generator，沿用像素散步的 `Runner`：`yield 秒數` 等那麼久、`yield null` 等一格、`yield 函式` 等到它回傳 true。指令也是 generator，用 `yield*` 呼叫，P2 的系統用 `registerCommand` 加上蓋章、店、拍照：

```ts
function* (s) {
  yield* s.say('今天的風很舒服。')
  const i = yield* s.ask('要嗎？', ['要', '不要'])
}
```

引擎對外只發型別化的事件（`say`、`ask`、`mapEnter`、`sfx`、`bgm`、`menu`、`camera`、`interact`、`clock`、`save`、`step`…），一個聽的人丟錯不影響其他人。沒有人聽 `say` 時腳本直接往下，所以 vitest 可以不開畫面跑完整條流程（`play/flows.test.ts`）。

### 畫面上的提示（P4）

- 按鍵提示列：`ui/hints.ts` 是純函式，PlayView 每 4 次更新（約 0.07 秒）照現在的情境（走路、面前是什麼、對話、手帳、取景框、各種面板）組一份狀態，回傳要列的鍵與動詞；手機不放提示列，改成讓相機鈕這類按鈕亮起來、換上當下的字。
- 地名：`engine/places.ts` 只從地圖本身的資料找「有名字的地方」（告示牌的標題、門通往的室內），不另外編名字；`ui/nearby.ts` 決定什麼時候浮出（2 格內、同一個地方 90 秒內不重複、剛進地圖時腳下附近的先當作看過）。
- 小地圖：`engine/minimap.ts` 一格 tile 一個點，照 tile 名字與碰撞分成 13 類（路、廣場、草、田、水、深海、樹、牆、建築、山、鐵路…），顏色也是 px token。進一張地圖時算一次（64×48 約 3,000 格）。

## 7. 你的旅人變像素人（`game/avatar/`）

正面的步驟（`generate.ts`、`pixelize.ts`、`kmeans.ts`，都是純函式）：

1. 用旅人頁同一套紙娃娃 SVG 圖層畫成大圖，邊畫邊做 chibi 變形：頭以脖子為中心放大 1.2 倍，身體寬 ×0.92、高 ×0.72。
2. 大圖的解析度是成品的 8 倍（每個像素 8×8 個細格）。
3. 從正面取 6,000 個、背面取 3,000 個不透明的點，在 OKLab 裡做 k-means 分 10 色（四個方向共用）；每群的顏色取群裡原本 RGB 的平均，留住 token 的顏色。
4. 多數決縮小：每個像素的 64 個細格各自對到最近的顏色再投票，OKLab 的 L 低於 0.36 的深色票數 ×2.5，細線、眼睛不會被淺色吃掉；細格的不透明度不到一半就是透明。
5. 蓋眼睛（帽子、面具擋住的照實不畫）→ 清孤立像素 → 圖層交界加深（相鄰的不同圖層 ΔE(OKLab) < 0.11 時，後面那格深一階，帽子與臉、面具與頭髮才分得開）→ 1px `px-ink` 外框。

遊戲裡本體 20×28、畫布 32×40；`/about` 的像素散步本體 16×24、畫布 24×34。背面是便宜的 2D（頭整顆填髮色、後髮在上、最後疊帽子）。走路是站、左步、右步三格，邁步時身體上移 1px、抬起的腳再高 1px。夥伴縮成 8 色、最大 16px。

**側面用 3D**（`side3d.ts`）：旅人頁的 3D 旅人是把 2D 剪影「充氣」做的（`services/avatar3d/inflate.ts`：距離場決定厚度 h = bulge × √d，marching squares 沿輪廓切網格）。側面直接拿它來算：

- 拿掉夥伴與影子，頂點照同一個 chibi 變形，前後厚度身體 ×1.6、頭 ×1.1（充氣的身體太薄，轉到側面只剩 3–4px）。
- 正交鏡頭轉約 73 度（`SIDE_YAW = -(π/2 - 0.3)`；正側面時頭髮會蓋住整張臉）。
- 只開環境光、強度 π：輸出的顏色就是貼圖原本的顏色，沒有明暗，像素化時對得回同一組 10 色。
- `preserveDrawingBuffer` 讀回像素，走同一套多數決、補一隻眼睛，右邊用左邊翻。
- three.js 只在這裡動態載入，`avatar/three3d.ts` 只 re-export 用到的 8 個類別（整個命名空間 import 會讓那一檔多出用不到的東西）。沒有 WebGL 或任何一步失敗就用參數化的側面範本，遊戲照樣起得來；只在閒下來時算（標題、手帳、暫停、換地圖）。

快取：key 是 `v{版本}:{寬}x{高}:hash(外觀＋各位置的單品＋紙娃娃顏色的指紋)`，放記憶體與 IndexedDB `hitomeguri-traveller`（最多 8 筆）；localStorage 留一個指標給 `/about`，所以形象網站不用載 three.js、不用打 Firestore 就能讓散步的人換成你的旅人。

## 8. 聲音（`game/audio/`）

全部用 Web Audio 程式合成，沒有音檔。聲道仿 GBA：

| 聲道 | 做法 |
|---|---|
| 方波 ×2 | `PeriodicWave`，佔空比 12.5／25／50%。係數用等寬階梯波的傅立葉級數解析解直接算；瀏覽器會依音高拿掉會疊頻的高次諧波 |
| 波形表 | 32 格、每格 4-bit，寫成 32 個 16 進位字，同樣轉成係數，保留階梯的味道 |
| 雜訊 | 15-bit LFSR 產生 buffer：長週期 32,767 步是沙沙的白雜訊，短週期 127 步帶音高、有金屬感；音高靠一秒走幾步調 |
| 撥弦 | Karplus–Strong 預先算成一段樣本，加音高修正，當三線 |
| 太鼓 | 正弦往下掃頻，疊一小段雜訊當鼓皮 |

混音：曲子 → BGM → master → 9.5 kHz 低通 → 軟限幅（0.7 以下不變、最多到 0.92）。音量封包是 GainNode 的 ramp，顫音是 LFO 接 `detune`。

**曲子寫成 tracker 字串**，一軌一列，一個字一格：

```ts
// songs/kyoto.ts：都節音階（E F A B C）、96 bpm、八分音符一格、16 小節約 40 秒
const MELODY = 'E5 - B5 - A5 B5 C6 - | B5 - A5 F5 E5 - - - | …'
//  音名＋八度＝開始一個音、- 延長、. 休止、| 小節線（不佔格，只用來檢查格數）
//  打擊是單一字母（h s t c o／D d K k），後綴 ^ 重音、_ 輕
```

曲子另外寫 `night`（夜裡慢多少、哪些軌拿掉）與 `festival`（祭典才有的太鼓軌），同一首換狀態不會從頭來。每首寫明音階（都節、琉球、陽音階、D 大調、F 大調五聲），vitest 檢查每個音都在那個音階裡。

**排程**是純函式（`schedule.ts`，可以測）：游標記「下一格是從開始算的第幾格」與時間基準。即時播放每 25 ms 叫一次 `pump`，排好之後 120 ms 內要開始的音；計時器被拖住、遲到超過 20 ms 的格直接跳過，不會一口氣補響。換速度在下一格重定基準；loop 只是把「第幾格」換算成曲子的第幾格，時間軸不回頭，接縫不會錯開。

其他：BGM 5 首（京都、沖繩、東京、北海道的鎮與室內，全部原創；奈良、大阪、兵庫用京都那首）、jingle 3 段（到鎮、蓋章、買到東西，放的時候鎮曲壓到 18%）、效果音 19 個。按「開始／繼續」那一下才建 `AudioContext`（iOS 要在手勢裡），之後只要 `state()` 不是 running，每次按鍵都再 unlock 一次；分頁在背景、P 暫停時 suspend，暫停的原因分開記。沒有 Web Audio 時換成靜音的空實作。各曲在 Chromium 量過響度（−31 到 −37 dB(A)），把太大聲的北海道調小過。

## 9. 資料流

```
data/（景點、地圖、鐵路、市区町村、祭典、地區特色、老舖・城、季節、航線）
  └─ python -m pipeline.cli build-bundles
       ├─ bundles/game/{縣}.json   game_bundle.py：只留選到的鎮的景點（每鎮前 16 個）、簡介第一句（160 字內）、
       │                            縣內路網＋選到的車站兩兩之間的最短路徑
       └─ bundles/game/_world.json  game_world.py＋game_taiwan.py：7 縣的鎮、代表站、縣之間 20 條交通（10 對、兩個方向）、
                                    台灣出發的航線與每個機場到各鎮的路
前端
  playPrefetch.ts：一進 /play 只抓 _world 與京都
  world/data.ts：bundle → PrefData（測試直接吃 web/src/game/fixtures/*.json，同一個形狀）
  坐車到還沒讀的縣：車窗一出來就開始讀那一縣（與要的 kit），最多等 20 秒；讀不到就回到出發的地方說「現在去不了。」
```

- 每縣的 game bundle（gzip）：京都 75 KB、沖繩 41 KB、奈良 46 KB、大阪 70 KB、兵庫 69 KB、東京 99 KB、北海道 71 KB；世界索引 P3 是 4.3 KB，P4 加了台灣的航線後 7.5 KB。
- 鐵路距離是全國 rail-graph 的最短路徑（新幹線的權重同日帰り；路徑上新幹線 ≥ 20 km 的那一段標新幹線）；飛機、巴士是兩個代表點的直線 km。畫面上只寫距離，不寫時刻、班次、路線名。km 的小數兩邊照同一個規則（Python `round(x, 1)`＝前端的 `round1`），測試對過。
- **台灣出發的航線**：`seed-taiwan-routes` 讀国土交通省每季發表的「各空港における国際線就航状況調べ」Excel（工作表「直行＜データ＞」，一列是一條航線的一家航空公司），只留「国・地域」是台灣的列，日本的機場對到 `data/seed/airports.json`。結果 34 條（台北 23、台中 3、高雄 8），每條有航空公司與每週班次；台北不分桃園、松山，所以遊戲裡寫「台北」。航空公司的中文名取各家的繁中官網（`data/flights/airline_names.json`，每筆有網址）。
- `game_taiwan.py` 把航線接到鎮：機場是某一鎮的機場（那覇、新千歳）就降在那一鎮的機場大廳；在遊戲的縣裡、但不是哪一鎮的（関西、羽田、函館）另外做一間大廳；不在遊戲的縣裡的（成田、中部）沒有大廳，飛到之後直接坐電車到鎮上。機場到鎮的鐵路最多 250 km、沒有車站的機場巴士最多 30 km（遊戲規則）。「想去的地方」的路線照「地面距離短的先、再看每週班次」排。台灣那一邊沒有座標，飛機那一段不寫 km。
- 分檔：遊戲程式 `game-*.js`、關東與北海道的 tile `game-kits-*.js`、畫面 `PlayView-*.js`、three.js `Avatar3D-*.js`、與像素散步共用的 `pxcore-*.js`。都不放進 PWA 的預先快取。部署之後還開著的舊分頁抓不到舊 chunk（404／410，或伺服器回 `text/html`）時，先存檔、同一個網址重新載入一次；瀏覽器會記住失敗的 `import()`，所以重試時網址加 `?r=n`。

## 10. 存檔

| 放什麼 | 在哪裡 |
|---|---|
| 遊戲（地圖、格子、方向、旗標、現金、行李、印、房間擺設、日曆、看過的告示牌、相簿索引；系統的部分在 `ext.systems`） | localStorage `hitomeguri:game:v1:<uid 或 guest>`，一份 JSON，50 KB 以內 |
| 照片（PNG） | IndexedDB `hitomeguri-game` 的 `photos` |
| 旅人 sprite | IndexedDB `hitomeguri-traveller`（最多 8 筆）＋ localStorage 指標 `hitomeguri:traveller:v1:<uid>` |
| 設定 | localStorage `hitomeguri:game:ui:v1`、聲音 `hitomeguri:game:audio:v1`（裝置層級，不跟存檔走） |

- 讀寫都包 try/catch；壞掉的、版本不認得的存檔當作沒有，欄位型別不對的換成預設值。沒有 IndexedDB 時照片只放記憶體，遊戲照樣能玩。
- 舊存檔怎麼接：生成器版本變了、或找不到存的地圖，就把玩家放回那一鎮的車站，旗標與東西都留著。P4 的旅費從「文」改成「円」：第一次讀到舊存檔時 ×10、至少 50,000 円；換過的記號與刷卡累計放在 `state.flags`（`wallet:yen`、`wallet:card`），因為部署之後還開著的舊分頁讀寫存檔時會原樣留著 flags，記號不會掉（掉了就會再 ×10 一次）。新遊戲從台灣出發不影響已經在日本的存檔。
- 不碰 Firestore：存檔只在這台裝置，`firestore.rules` 不用改；遊戲也不寫網站的 wallet、cards、achievements、去過。

- CI 沒有 bundles（`web/public/bundles` 不進 repo），所以測試只讀 commit 進去的 `web/src/game/fixtures/`（`build-fixtures.mjs` 從 game bundle 拷子集，P3 起每縣 73–108 KB）。
- **pytest**：`test_game_bundle.py`、`test_game_world.py`（名城的上限、北海道的分散、代表站不重複、縣之間的 km）、`test_game_taiwan.py`、`test_taiwan_routes.py`。
- **瀏覽器走查**：沙箱裡不開長駐的 dev server，每次在同一個指令裡開暫時的 vite（需要登入時加 Firebase Emulator）＋Playwright（Chromium 在 `/opt/pw-browsers`），跑完關掉。DEV 時 `window.__game` 可以傳送、改日期時段、換天氣、給錢、跳過對話、讀狀態；`window.__gameAudio` 可以試聽。每一輪 QA 跑同一個矩陣：桌機 1280×800、iPhone 390×844 直拿、844×390 打橫、減少動態，加上幾份舊存檔（P2 的京都、P3 的函館、東京），最後看 console 有沒有錯誤（沙箱擋掉 Google Fonts 造成的訊息另外列）。

- **審查**：每個階段做完由另外的 agent 從幾個角度（正確性、內容真實性與規則、手機、手感、效能）找問題，每個問題再由另一個 agent 重現，不成立的刪掉（流程與數字見 [skill-回顧.md](skill-回顧.md)）。

## 13. 已知限制

- 沒有在真機（iOS Safari、Android）上測過：觸控、safe-area、3D 側面的速度、P4 的提示列與小地圖都是 Chromium 的模擬。沒有用喇叭聽過，音量與音色要人聽過再調。
- 換時段那 1.2 秒每格畫兩次世界，降速 4 倍時超過 4 ms。直接開 `/play` 會先下載首頁的 maplibre（首頁靜態引入 ExploreView 的取捨）。
- 一鎮的生成最久約 80 ms，超過 50 ms 的目標。北海道 kit 的 tile id 快用完（約 6116／6143），再加要開新的一段。
- 沒有「今年」的花況（只用平年值）；渡輪做好了但資料沒有路線；台灣那一邊沒有座標，所以飛機那一段沒有距離；接不到任何鎮的機場（石垣、仙台、小松…）在出發看板上是灰的。
- Safari 的 `import()` 錯誤不帶網址：kit 檔換網址重試、舊分頁偵測在 Safari 上只能說「現在去不了。」，要自己重新整理。
- fixtures 共約 1.1 MB（京都、沖繩約 610 KB，超過原本 500 KB 的預算）。訪客與登入使用者的照片在同一個 IndexedDB。
